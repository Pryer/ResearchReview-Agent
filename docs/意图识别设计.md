# 通用用户意图识别系统设计方案

## 1. 项目目标

实现一个面向多类型用户请求的通用意图识别系统。

系统接收：

* 当前用户消息；
* 最近若干轮对话；
* 可用工具与能力列表；
* 用户上传文件、页面或上下文信息。

系统输出：

1. 用户正在讨论什么；
2. 用户想完成什么；
3. 用户希望对什么对象执行什么操作；
4. 用户期望得到什么结果；
5. 需要调用哪些能力或工具；
6. 当前信息是否足够执行；
7. 是否需要澄清；
8. 存在哪些风险、约束或隐含条件。

系统不得只输出类似：

```json
{
  "intent": "education"
}
```

应输出可执行的结构化任务描述。

---

# 2. 核心设计原则

## 2.1 意图不是单标签

用户请求通常由多个维度组成：

```text
意图 =
领域
+ 对象
+ 操作
+ 方法
+ 目标
+ 交付物
+ 约束
+ 上下文
```

例如：

> 调研近三年使用视觉和语音技术进行课堂行为编码，并分析师生互动的论文。

不能仅识别为：

```text
教育
```

也不能仅识别为：

```text
计算机视觉
```

正确结果应包括：

```text
教育场景
+ 课堂行为
+ 文献调研
+ 自动行为编码
+ 视觉与语音方法
+ 师生互动分析
+ 研究背景与研究现状
```

---

## 2.2 区分最终目标和中间手段

必须分别识别：

* 用户最终想得到什么；
* 用户打算通过什么方式得到；
* 哪些步骤只是中间步骤。

例如：

> 用OCR提取合同内容，然后总结风险条款。

其中：

```text
最终目标：合同风险分析
中间手段：OCR
```

不能识别为单纯的OCR任务。

---

## 2.3 允许一个请求包含多个意图

例如：

> 查找会议邮件，总结讨论内容，并在明天下午安排一个跟进会议。

包含三个操作：

1. 搜索邮件；
2. 总结内容；
3. 创建日历事件。

系统必须输出任务图，而不是选择其中一个作为唯一意图。

---

## 2.4 优先执行，必要时才澄清

信息不足不等于必须追问。

系统应区分：

* 可合理推断的信息；
* 可使用默认值的信息；
* 缺失后会导致执行结果完全不同的信息。

只有第三类信息才触发澄清。

---

# 3. 总体架构

推荐使用以下处理链：

```text
用户输入
    ↓
上下文整理
    ↓
语义槽位抽取
    ↓
候选任务生成
    ↓
任务依赖分析
    ↓
歧义与缺失信息判断
    ↓
能力与工具路由
    ↓
执行计划生成
```

系统包含五个核心模块：

```text
Context Builder
Intent Parser
Task Graph Builder
Clarification Policy
Capability Router
```

## 4.2 Domain：应用领域

领域只描述任务发生在哪个业务或知识场景中。

```json
{
  "id": "education",
  "label": "教育",
  "confidence": 0.95,
  "evidence": ["课堂", "学生", "教师"]
}
```

```text

marketing
design
content_creation
product_management
human_resources
travel

```

允许多个领域：

```json
"domains": [
  {
    "id": "education",
    "role": "application_domain"
  },
  {
    "id": "artificial_intelligence",
    "role": "method_domain"
```

# 5. 任务图设计

## 5.1 为什么使用任务图

复杂请求通常不是一个操作，而是一系列有依赖关系的操作。

例如：

> 找30篇论文，筛选近三年文献，写研究背景和研究现状。

任务关系：

```text
检索论文
  ↓
验证年份
  ↓
筛选相关论文
  ↓
分类整理
  ↓
综合分析
  ↓
撰写研究背景
  ↓
撰写研究现状
  ↓
生成参考文献
```

---

## 5.2 Task Node结构

```json
{
  "task_id": "task_01",
  "action": "search",
  "object": "academic_papers",
  "goal": "collect_recent_research",
  "inputs": [],
  "outputs": ["candidate_papers"],
  "depends_on": [],
  "required_capabilities": [
    "web_search",
    "academic_search"
  ],
  "status": "pending",
  "confidence": 0.96
}
```

# 6. 意图识别流程

## 6.1 第一步：上下文整理

Context Builder 输入：

```json
{
  "current_message": "...",
  "conversation_history": [],
  "attachments": [],
  "available_tools": [],
  "user_profile": {}
}
```

输出：

```json
{
  "resolved_message": "...",
  "references": {},
  "active_topic": "...",
  "previous_constraints": [],
  "unresolved_pronouns": []
}
```

需要完成：

* 代词消解；
* “这个”“继续”“按照刚才的”等引用解析；
* 合并之前已确认的约束；
* 识别用户是否在修改之前的任务；
* 识别用户是否在回答澄清问题。

---

## 6.2 第二步：语义槽位抽取

Intent Parser 必须独立抽取：

```text
Domain
Object
Operation
Method
Goal
Deliverable
Constraint
```

不要直接先分类，再根据分类填槽位。

推荐提示词：

```text
请将用户请求解析为结构化任务。

不得只给出单一意图标签。

分别识别：
1. 请求发生的应用领域；
2. 用户希望处理的对象；
3. 用户希望执行的操作；
4. 用户指定或暗示的方法；
5. 用户最终希望实现的目标；
6. 用户期望的交付物；
7. 明确约束；
8. 隐含但合理的假设；
9. 可能存在的歧义；
10. 各字段置信度。

特别区分：
- 最终目标与中间手段；
- 业务场景与技术方法；
- 用户明确要求与系统推断；
- 单任务与多任务；
- 信息检索与内容生成；
- 内容生成与实际执行。
```

---

## 6.3 第三步：生成候选解释

对于歧义请求，不应立即选择唯一解释。

例如：

> 帮我做课堂行为分析。

生成：

```json
{
  "hypotheses": [
    {
      "id": "h1",
      "description": "人工课堂观察与教育学分析",
      "confidence": 0.32
    },
    {
      "id": "h2",
      "description": "使用计算机视觉识别课堂行为",
      "confidence": 0.28
    },
    {
      "id": "h3",
      "description": "自动行为编码后进行教育分析",
      "confidence": 0.40
    }
  ]
}
```

候选解释只用于内部决策，不直接暴露给执行模块。

---

## 6.4 第四步：候选解释排序

候选排序考虑以下证据：

```text
当前句中的明确动作词
当前句中的目标词
上下文中已确认的方向
用户提供的文件类型
请求的最终交付物
用户此前使用的术语
可用工具
```

推荐评分：

```text
score =
0.30 × explicit_goal_match
+ 0.20 × operation_match
+ 0.15 × context_match
+ 0.15 × deliverable_match
+ 0.10 × method_match
+ 0.10 × domain_match
```

领域匹配权重不能过高，否则容易出现“看见课堂就路由教育、看见YOLO就路由视觉”的错误。

---

# 7. 澄清策略

## 7.1 触发澄清的条件

满足以下任一条件时才考虑澄清：

```text
最高候选置信度 < 0.55
```

或：

```text
前两名候选置信度差值 < 0.15
且会导致不同执行流程
```

或：

```text
缺失硬约束会导致无法执行
```

或：

```text
任务涉及不可逆操作，但关键对象不明确
```

例如：

* 发给谁；
* 删除哪个文件；
* 修改哪个日历事件；
* 使用哪个仓库；
* 购买预算是多少。

---

## 7.2 不应触发澄清的情况

以下情况优先使用合理假设：

* 输出格式未指定，但有明显默认格式；
* 用户要求总结，但没有指定长度；
* 用户要求调研，但没有指定数据库；
* 用户要求生成文档，但没有指定字体；
* 用户要求代码实现，但次要命名细节缺失。

---

## 7.3 澄清问题设计规则

澄清问题必须满足：

1. 一次只问一个高信息量问题；
2. 问题会直接改变执行方案；
3. 优先给具体选项；
4. 不要求用户重复完整需求；
5. 不询问系统可以自行推断的信息。

错误：

```text
请详细说明您的需求。
```

正确：

```text
你更关注自动行为识别算法，还是自动编码后的教育分析？
```

更好：

```text
这项研究的重点是哪一种？
1. 课堂行为识别算法
2. 人工课堂观察编码
3. 自动编码后分析教学互动
```

---

## 7.4 带假设执行

当置信度中等但仍可安全执行时，使用：

```json
{
  "clarification": {
    "required": false
  },
  "assumptions": [
    "将课堂行为分析理解为自动编码与教育分析结合"
  ]
}
```

执行模块可在结果开头简短说明采用的理解。

# 8. 能力路由设计

## 8.1 路由不是领域分类

错误：

```text
教育请求 → 教育Agent
代码请求 → 编程Agent
```

正确：

```text
根据任务节点分别路由能力
```

例如：

> 查邮件内容，生成回复，然后安排会议。

对应能力：

```text
邮件搜索
邮件阅读
文本总结
邮件撰写
日历创建
```

---

## 8.2 Route结构

```json
{
  "route_id": "route_01",
  "task_id": "t2",
  "capability": "web_search",
  "tool": "web.run",
  "required": true,
  "priority": 1,
  "fallback": "internal_knowledge"
}
```

---

## 8.3 能力注册表

系统维护一个 Capability Registry：

```json
{
  "capability_id": "academic_search",
  "description": "搜索并核验学术论文",
  "supported_operations": [
    "search",
    "retrieve",
    "verify"
  ],
  "accepted_objects": [
    "academic_paper",
    "doi",
    "journal"
  ],
  "required_inputs": [
    "query"
  ],
  "optional_inputs": [
    "year_range",
    "domain",
    "minimum_count"
  ],
  "output_schema": "AcademicPaper[]"
}
```

---

## 8.4 路由评分

```text
route_score =
0.35 × operation_support
+ 0.25 × object_support
+ 0.20 × input_availability
+ 0.10 × output_compatibility
+ 0.10 × reliability
```

---

## 8.5 多能力组合

每个任务节点可以调用多个能力：

```json
{
  "task_id": "t3",
  "routes": [
    {
      "capability": "metadata_lookup",
      "role": "primary"
    },
    {
      "capability": "doi_verification",
      "role": "validation"
    }
  ]
}
```

# 9. 意图本体设计

不要建立数千个具体意图名称，例如：

```text
search_classroom_behavior_papers
search_medical_ai_papers
search_finance_risk_papers
```

应建立通用组合式本体。

---

## 9.1 一级意图类别

```text
information_request
content_generation
content_transformation
analysis
recommendation
planning
execution
monitoring
software_development
artifact_creation
communication
account_or_setting_change
```

---

## 9.2 二级操作

例如 `information_request`：

```text
search
lookup
verify
compare
explain
summarize
```

例如 `software_development`：

```text
design
implement
debug
review
test
```

# 12. Prompt实现方案

## 12.1 Parser System Prompt

```text
你是通用任务语义解析器。

你的任务不是把用户请求归入一个单一标签，而是将其转换为可执行的结构化任务描述。

必须识别：
- 应用领域 domains
- 操作对象 objects
- 用户动作 operations
- 方法 methods
- 最终目标 goals
- 交付物 deliverables
- 约束 constraints
- 任务依赖 task_graph
- 歧义 ambiguities
- 缺失信息 missing_slots
- 假设 assumptions
- 置信度 confidence

规则：
1. 区分应用场景、技术方法和最终目标。
2. 不要因为出现领域词，就忽略技术任务。
3. 不要因为出现技术词，就将技术误认为最终目标。
4. 一个请求可以包含多个操作。
5. 将复杂请求拆成有依赖关系的任务节点。
6. 只有缺失信息会显著改变执行方案时，才要求澄清。
7. 能合理推断的信息放入 assumptions。
8. 用户明确表达的信息标记为 explicit。
9. 根据上下文继承已确认条件。
10. 输出必须符合指定JSON Schema。
```

---

## 12.2 Router System Prompt

```text
你是任务能力路由器。

输入包含：
- 结构化任务图；
- 当前可用能力列表；
- 每个能力支持的操作、输入和输出。

你的任务是为每个任务节点选择最合适的能力。

规则：
1. 按任务节点路由，不按整个请求路由。
2. 一个请求可以使用多个能力。
3. 只有能力输入条件满足时才能选择。
4. 优先使用可靠且能直接完成任务的能力。
5. 为每个路由输出理由、优先级和备用方案。
6. 不得选择与任务操作不匹配的能力。
```

# 14. 核心伪代码

```python
def process_request(message, history, capabilities):
    context = build_context(
        message=message,
        history=history
    )

    parsed = parse_semantic_frame(context)

    normalized = normalize_entities_and_operations(parsed)

    hypotheses = generate_hypotheses(
        context=context,
        semantic_frame=normalized
    )

    ranked = rank_hypotheses(
        hypotheses=hypotheses,
        context=context
    )

    selected = ranked[0]

    task_graph = build_task_graph(selected)

    ambiguity_result = evaluate_ambiguity(
        ranked_hypotheses=ranked,
        task_graph=task_graph
    )

    missing_slots = detect_missing_slots(task_graph)

    clarification = decide_clarification(
        ambiguity=ambiguity_result,
        missing_slots=missing_slots,
        risk=selected.safety
    )

    if clarification.required:
        return {
            "status": "needs_clarification",
            "intent": selected,
            "question": clarification.question
        }

    routes = route_capabilities(
        task_graph=task_graph,
        capabilities=capabilities
    )

    return {
        "status": "ready",
        "intent": selected,
        "task_graph": task_graph,
        "routes": routes
    }
```

# 15. 规则引擎与LLM的职责分工

## 15.1 LLM负责

* 理解自然语言；
* 代词和上下文解析；
* 槽位抽取；
* 候选解释生成；
* 复杂任务拆解；
* 隐含目标推断；
* 自然语言澄清问题生成。

## 15.2 规则引擎负责

* JSON Schema校验；
* 枚举标准化；
* 时间、金额、数量解析；
* 置信度阈值；
* 工具输入完整性检查；
* 不可逆操作限制；
* 路由兼容性校验；
* 硬约束检查。

## 15.3 不推荐

不要完全依赖：

```text
关键词规则
正则表达式分类
固定意图枚举
单次LLM分类
```

推荐：

```text
LLM语义解析
+ JSON Schema
+ 规则校验
+ 能力注册表
+ 回归测试
```

# 18. 验收标准

系统达到以下标准后方可上线。

## 18.1 结构化输出

* 95%以上请求可输出合法JSON；
* 所有输出通过JSON Schema校验；
* 不允许出现未注册的核心操作枚举；
* 允许通过 `custom_attributes` 扩展长尾属性。

## 18.2 意图理解

* 明确单任务操作识别准确率不低于95%；
* 多任务请求任务召回率不低于90%；
* 技术手段与最终目标区分准确率不低于90%；
* 跨领域请求识别准确率不低于85%。

## 18.3 澄清

* 不必要澄清率低于10%；
* 关键缺失信息漏问率低于5%；
* 每次只生成一个关键澄清问题。

## 18.4 路由

* 工具路由Top-1准确率不低于90%；
* 多工具任务完整路由准确率不低于85%；
* 不可逆操作误执行率为0。

# 20. 最终原则

系统内部不要问：

```text
这个请求属于哪个类别？
```

应问：

```text
用户希望对什么对象，
执行哪些操作，
使用什么手段，
最终得到什么，
需要哪些能力，
哪些步骤存在依赖，
当前信息是否足够执行？
```

最终实现目标是：

```text
自然语言请求
→ 结构化语义框架
→ 可执行任务图
→ 能力路由计划
```

而不是：

```text
自然语言请求
→ 单一意图标签
```
